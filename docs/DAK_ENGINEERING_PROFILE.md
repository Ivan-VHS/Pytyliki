# Конституция Уточек — профиль инженерного применения Pytyliki

**Статус:** проектный контракт для существующей C11-рабочей станции. Документ не превращает Pytyliki в язык AETHER-ANAS и не объявляет запланированные возможности реализованными.

## 1. Границы продукта

Pytyliki — модульная C11-рабочая станция для чтения характеристик CPU/ISA, ограниченных локальных тестов, анализа исходников, PCM16 WAV/DSP и инженерных отчётов. Пользовательские интерфейсы — CLI для Windows/Linux и нативный Win32 GUI. Общие операции принадлежат единому core API.

Применение Конституции Уточек означает целостный продукт с внутренне модульной архитектурой; явные границы между вычислениями, файловыми операциями, платформенными адаптерами и политикой; ограниченные ресурсы; проверяемые capability reports вместо догадок о железе; спокойный интерфейс и документацию, точно совпадающую с кодом.

**Не является целью Pytyliki:** новый язык, компилятор AETHER-ANAS, гиперграфовая база программ, GPU/FPGA/cloud runtime, ОС, firmware writer либо автономный агент с неограниченной записью.

## 2. Шесть статей в терминах Pytyliki

| Статья | Прикладное значение | Состояние |
|---|---|---|
| I. Трёхсредность | Суша — локальные CPU/память и детерминированные тесты; Вода — ограниченные DSP/PCM потоки; Небо — удалённые и распределённые узлы только как будущая интеграция с отдельными сетевыми контрактами | Local и bounded DSP — область проекта; distributed — Planned/N/A |
| II. Гидродинамическое спокойствие | CLI/GUI — тонкие адаптеры одного core; диагностика и отчёты раскрывают измерения, ошибки и недоступность телеметрии | Реализуется через модульность и отчёты; автоматическая генерация README не заявляется |
| III. Утиный полиморфизм | C11 API использует явные структуры, enum, валидаторы и контрактные тесты | Partial; статический типовой движок языка не относится к продукту |
| IV. Перьевая смазка | Анализ CPU и исходников остаётся read-only; будущие записи проходят policy, авторизацию, staging и rollback | Read-only и deny-by-default policy — базовые гарантии |
| V. Стая | Параллелизм допускается только при явном бюджете, отмене, ограниченных очередях и тестировании гонок/порядка | Planned/Partial; нет автоматического swarm или distributed runtime |
| VI. Округлость | Единые сообщения, команды и документация; минимум когнитивного шума, без скрытых аппаратных действий | Обязательство для каждого изменения и README |

### Три среды — не три неподтверждённых backend

- **Суша:** локальная работа с CPU и памятью, текущие benchmark и анализы.
- **Вода:** потоковая обработка аудио/DSP с ограничениями блока, длины, формата и памяти.
- **Небо:** сеть, кластер, GPU и распределённая маршрутизация не подразумеваются наличием CPU-инвентаризации или APSIA-планировщика. Они требуют реального backend, fail-closed policy, модели сетевых отказов и отдельных тестов.

## 3. Десять отречений — безопасная адаптация

| № | Идея исходного манифеста | Инженерное правило Pytyliki |
|---:|---|---|
| 1 | От монополии одномерного текстового файла | Для текущего приложения сохраняются C-исходники и Git; графы могут быть дополнительной визуализацией, но не заменой исходников без доказанной миграции. |
| 2 | От имён как идентификаторов | Для артефактов и отчётов применять commit SHA, content hashes и версии схем; C API и пути остаются читаемыми. |
| 3 | От GC и ручного учёта | В C11 явно документировать ownership/lifetime; проверять освобождение на всех ветках. Не обещать region GC/FBIP без отдельной реализации. |
| 4 | От лицензионного принуждения | Соблюдать текущую MIT-лицензию и provenance зависимостей; не менять лицензию автоматически и не обещать CC0. |
| 5 | От compile/runtime пропасти | Планирование и валидация выполняются до выполнения; будущие генераторы обязаны иметь dry-run и лимиты. |
| 6 | От null/неявных исключений | Использовать явные return codes/status, проверяемые выходные параметры и документированные ошибки C API. |
| 7 | От небезопасных циклов/индексов | Проверять длины и границы до индексирования; DSP-блоки и коллекции ограничивать. |
| 8 | От монолитного класса | Разделять данные, поведение, формат отчёта и физический backend по независимым контрактам. |
| 9 | От слепого доверия внешним данным | Валидировать пути, размеры, WAV headers, JSON, CPU flags и внешние артефакты; неизвестное значение не считать нулём. |
| 10 | От непрозрачной стоимости | Для benchmark/DSP указывать пределы и измеримые параметры; heuristic scores не выдавать за ускорение или гарантию. |

## 4. Двенадцать заповедей инженерной практики

1. Уникальность — новая подсистема должна закрывать конкретный сценарий Pytyliki.
2. Однозначность — публичные API и CLI-параметры имеют одно значение и один результат.
3. Ортогональность — новые функции используют общий core вместо параллельной логики GUI/CLI.
4. Человекоцентричность — диагностика показывает причину, компонент, путь исправления и код возврата.
5. Отклик — стоимость операций измеряется; универсальный порог 16 мс не объявляется без целевой платформы и сценария.
6. Самодостаточность — core должен собираться и тестироваться отдельно от необязательных адаптеров.
7. Мосты — внешние API/FFI требуют ABI-контракта, ownership, валидации и contract tests.
8. Постепенность — сначала discovery и отчёт, затем локальные bounded workloads, далее optional integrations.
9. Экологичность — ограничивать память, время, потоки, очереди и объём логов.
10. Стабильность — C11 и публичные заголовки изменять осознанно; несовместимые изменения документировать.
11. Открытость — схемы JSON, метрики, C API и документы доступны для инструментов и аудита.
12. Радость творчества — аккуратный UX важен, но не подменяет корректность и доказательства.

## 5. Шестьдесят шесть законов — инженерные обязательства

Нумерация исходного манифеста сохранена. Каждая аналогия переведена в проверяемое требование к C11-приложению, а не в буквальное применение физических формул к коду.

### I. Физика и термодинамика (1–14)

1. **Сохранение энергии:** учитывать CPU-time, память, I/O и размер отчётов; не объявлять абстракции бесплатными без измерений.
2. **Рост энтропии:** поддерживать модульные границы C11, узкие заголовки и явные зависимости.
3. **Третье начало:** низкоуровневые адаптеры требуют явной платформенной проверки; не обещать абсолютную безопасность и идеальную скорость одновременно.
4. **Неопределённость:** различать измеренное, обнаруженное, доступное, неизвестное и неподдерживаемое состояние платформы.
5. **Закон Ома:** минимизировать лишние преобразования между CLI/GUI и общим core API.
6. **Сохранение заряда:** документировать владение буферами, WAV-файлами, дескрипторами и освобождение ресурсов на всех путях.
7. **Наименьшее действие:** обычный диагностический сценарий должен быть read-only и безопасным по умолчанию.
8. **Закон Кулона:** ограничивать связанность и область видимости; platform-specific код держать в адаптерах.
9. **Эффект Доплера:** одинаковый запрос должен иметь устойчивую семантику; особенности ОС показывать явно.
10. **Суперпозиция:** processor, DSP, scanner, policy и APSIA используют совместимые общие контракты.
11. **Закон Гука:** усложнение сценария не должно требовать каскадных правок независимых модулей.
12. **Броуновское движение:** совместное изменяемое состояние и фоновые задачи требуют модели синхронизации и тестов гонок.
13. **Принцип Паули:** запретить конфликтующие публичные символы и неоговорённые повторные владельцы ресурса.
14. **Запутанность:** межмодульные эффекты, записи и внешние вызовы проходят через декларированные интерфейсы.

### II. Механика и поток исполнения (15–26)

15. **Инерция Ньютона:** результаты анализа неизменяемы; изменения конфигурации/файлов требуют явной команды.
16. **Второй закон Ньютона:** минимизировать базовый runtime и зависимости; не создавать сервисную инфраструктуру без задачи.
17. **Действие и противодействие:** операции открытия/создания имеют симметричное закрытие, отчёт об ошибке и очистку.
18. **Тяготение:** предотвращать God Modules; один C-файл не должен собирать все подсистемы.
19. **Сохранение импульса:** передавать владение явно и не копировать большие буферы без измеренной причины.
20. **Бернулли:** потоковые DSP и будущие очереди должны иметь лимиты блока/буфера и поведение при переполнении.
21. **Архимед:** стандартный набор модулей должен быть достаточным, но не превращаться в монолит.
22. **Рычаг:** генераторы и автоматизация обязаны иметь dry-run, лимиты, provenance и отдельное разрешение на запись.
23. **Резонанс:** оптимизации должны учитывать реальные кэш-линии/ISA и подтверждаться профилем на целевых машинах.
24. **Трение:** внешние ABI/FFI требуют явных типов, соглашений вызова, владения и ошибок; zero-cost не заявляется без измерений.
25. **Навье—Стокс:** control flow модулей должен быть линейным и читаемым; скрытые переходы запрещены.
26. **Галилей:** платформенные различия не меняют контракт общего core; различия фиксируются в capability reports.

### III. Математика и логика (27–40)

27. **Гёдель:** статические/архитектурные проверки должны быть ограниченными и завершаться, а не обещать доказать всё.
28. **Остановка Тьюринга:** циклы, рекурсия, очереди, размеры файлов и benchmark-итерации должны иметь лимиты.
29. **Карри—Ховард:** использовать типизированные структуры C, enum result codes и валидируемые инварианты.
30. **Де Морган:** проверки опций и состояний симметричны; тестировать положительные и отрицательные ветви.
31. **Оккам:** не дублировать API и CLI-команды, если существующий модуль уже решает ту же задачу.
32. **Байес:** capability detection опирается на наблюдения с уровнем достоверности; unknown не превращать в ложное значение.
33. **Дирихле:** проверять сужение целых, переполнение, умножения размеров и границы буферов.
34. **Неподвижная точка:** callbacks и функции первого порядка имеют ясное владение и время жизни.
35. **Аксиома выбора:** правила маршрутизации APSIA и выбора backend возвращают однозначное решение или отказ.
36. **Теория категорий:** преобразования данных проверяются на композицию и идентичность.
37. **Большие числа:** частые сценарии диагностики и сборки просты; редкие опасные операции явно защищены.
38. **Кэли:** равнозначные пути CLI/GUI вызывают одно ядро, а не отдельные реализации алгоритма.
39. **Йонеда:** интерфейс определяется контрактом поведения и результата, а не именем/иерархией модулей.
40. **O-нотация:** README и API документируют объёмы и сложность benchmark/DSP операций.

### IV. Биология и эволюция (41–50)

41. **Естественный отбор:** новые функции сначала вводить экспериментально и принимать по фактам CI/использования.
42. **Гомеостаз:** ошибка необязательного модуля не ломает независимые read-only функции; восстановление только обратимое.
43. **Апоптоз:** старые API имеют период deprecation, тесты миграции и безопасное удаление.
44. **Симбиоз:** CMake, CTest, CI, GUI, CLI и документация составляют одну экосистему.
45. **Гаузе:** Pytyliki сохраняет нишу процессорной рабочей станции, а не имитирует универсальный компилятор или ОС.
46. **Геккель:** путь пользователя: обнаружение → базовая диагностика → отчёт → ограниченный benchmark → расширенный анализ.
47. **Иммунитет:** пути, файлы, числовые параметры, внешние отчёты и импортируемые данные проверяются на границах.
48. **Либих:** устранять узкое место, подтверждённое профилем, тестами или CI, а не предположением.
49. **Эпигенетика:** профили сборки меняют реализацию, но не скрытно искажают отчёт о возможностях.
50. **Нейропластичность:** CLI и GUI имеют понятные названия, единые ошибки и небольшой набор устойчивых понятий.

### V. Информатика и теория систем (51–64)

51. **Амдал:** параллелизм включать там, где он ускоряет измеряемую нагрузку, сохраняя последовательный fallback.
52. **Густавсон—Барсис:** масштабирование по ядрам/данным требует тестов на разных размерах задачи и лимитов ресурсов.
53. **CAP:** будущие сетевые функции описывают timeout, retry, partial failure и недоступность как состояния результата.
54. **Конвей:** модули позволяют независимую разработку через API и contract tests.
55. **Постел:** редакторы могут показывать неполный ввод, но отчёт/протокол остаётся строгим, машиночитаемым и валидируемым.
56. **Брукс:** единый стиль C, Markdown и форматирование сокращают затраты на координацию.
57. **Мур/Деннард:** проектировать буферы и массивы с учётом локальности и измеренного memory traffic.
58. **Дырявые абстракции:** предоставлять диагностику, метрики и инспекцию исходных отчётов и параметров benchmark.
59. **Хайрум:** случайный порядок хеш-таблиц и артефактов не становится публичным контрактом.
60. **POLA:** команда ведёт себя ожидаемо; нет скрытых записей, сетевых вызовов и elevation.
61. **CQS:** операции отчёта отделены от изменения конфигурации и прочих команд.
62. **Райс:** не угадывать намерение пользователя; неоднозначные параметры завершаются безопасной ошибкой.
63. **Вирт:** держать цикл configure/build/test быстрым и измеряемым; пороги задаются реальным CI.
64. **Галл:** развивать из небольшого работающего C11-ядра, не создавая преждевременную мегасистему.

### VI. Отладка и универсальность (65–66)

65. **Керниган—Плаугер:** оптимизировать код и документацию под чтение, ревью, отладку и воспроизводимость.
66. **Конвей—Тьюринг:** мощность каталога не важнее предсказуемых запретов; аппаратные записи и произвольное исполнение вне текущего продукта.

## 8. Обязательный gate для новых изменений

Изменение готово к ревью, если:
- указаны модуль, публичный API, владелец ресурсов, эффекты, лимиты и режим отказа;
- нет неявных записей, привилегированных операций и неограниченного выполнения;
- входы проверяются до выделения памяти, индексирования и арифметики;
- добавлены positive, negative, boundary и failure tests;
- CTest зарегистрирован; shared-core изменения прошли Windows/Linux build + test;
- ASan/UBSan и другие применимые анализаторы пройдены, а покрытие указано точно;
- README и локализованные README описывают фактическую реализацию, а не обещания;
- CI и независимое ревью привязаны к точному HEAD SHA; branch protection не обходится.

## 9. Лицензия и безопасность

Текущая лицензия Pytyliki — MIT. Этот профиль не меняет LICENSE. Любой импорт внешнего кода требует проверки лицензии, происхождения, зависимостей и build hooks.

Запрещено превращать рекомендации в скрытые аппаратные действия. Нет записи в firmware, BIOS/UEFI, microcode, registers, voltage, clocks, power limits, kernels или drivers. Планирование не получает полномочий на выполнение автоматически.
